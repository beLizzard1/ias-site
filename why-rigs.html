05 · How it is measured

Why both a SiL and a HiL apparatus

This note explains why the project builds two separate test rigs for the same system under test, rather than picking the cheaper one and living with it.

Background: why this project exists — why per-identity, directional evidence is worth building when population metrics like FAR/FRR are all that is otherwise available — and per-identity discriminatory power, on why two enrolled people may not get the same protection from the same system.

The customer sits in one of three places

An assurance engagement for an embedded face-recognition system is shaped almost entirely by where the customer sits relative to the system, because that determines what you are physically allowed to touch. There are three positions worth naming, because each rules a different apparatus in or out:

  • The manufacturer of the system. They own the models, so you can, in principle, get the model files and hook them up directly — feed in embeddings or images, read back whatever the model produces, no device needed at all.
  • An integrator using the model as a supply-chain component. They bought a chip or module with the model burnt in and want to know its impacts and limitations before they ship it inside their own product. What they can hand you is the end device, running the vendor's model, plus whatever custom application they wrote to feed data into it — the model itself is not available as a separate artefact.
  • An end user or deployer. Worst case, you can only interrogate the finished product — point a camera at it, present a card, watch what it does. This is close to black-box: no access to the model, often no access to the application layer, only the product's own sensor path.
Customer positionWhat you can touchApparatus that fits
ManufacturerThe models themselvesSiL
IntegratorEnd device + custom applicationHiL
End user / deployerThe product's own sensor inputHiL, via a controlled input path

Two apparatus map onto those three positions — not because two was a convenient number, but because the manufacturer's position and the integrator/end-user positions genuinely need different things from a rig.

SiL: the host runner

The software-in-the-loop apparatus is the host runner in idf_apps/ — the vendor's own ESP-DL runtime, built for the Linux target instead of the ESP32-S3, executing the same quantised .espdl model files the device ships with. It is cheap, fast, and fully observable: every tensor at every layer can be read out, which is what makes tensor-level diagnosis and regression/golden tests possible at all.

That observability is only useful if the SiL actually behaves like the silicon, and that faithfulness cannot be assumed — it has to be established. In this project it wasn't free: reaching a plausible SiL meant tracking down three defects in the vendor runtime's generic C/C++ fallback path — a Conv filter layout the host loader failed to unpack, a PReLU kernel that skipped requantisation on part of its output, and a memory planner that let every internal buffer alias the same offset when PSRAM wasn't configured — all in the fallback path that only a non-ESP32 host build exercises, since real ESP32-S3/P4 builds take the assembly-optimised paths and never touch it. Fixing those got the SiL to bit-exact agreement with an independent reference on every node, but that is agreement with a reference, not with the chip: whether the host's rounding matches the ESP32-S3's TIE728 kernels bit-for-bit is still open.

HiL: the real device

The hardware-in-the-loop apparatus is the actual ESP32-S3 with the model on it, driven by a custom application that feeds it data — the same shape as the integrator's position above. It is slower and less observable: you get back whatever the device is willing to expose, a verdict or a score, not the tensors behind it. What it gives you in return is that it is the ground truth. It is also the only way to answer the question the SiL cannot answer about itself: run the same images through both, compare the embeddings or verdicts, and the gap between them is the SiL's parity error.

Where even the application layer is not available — the end-user position — the same device has to be driven through the product's own sensor path instead of a custom feed. That is the black-box case: harder to control, but still HiL in spirit, since it is the real hardware doing the inference.

On why this target: see WhyDiscrimination.

What it took to build the SiL

Most of this project's effort so far has gone into the SiL, and the difficulty is itself an assurance finding, worth stating plainly.

ESP-DL is written for its own chips. The host/Linux target is a generic C/C++ fallback path the vendor rarely exercises — normal use takes the ESP32-S3/P4 assembly or PSRAM-aware paths instead. Just getting it to compile needed submodules initialised and an in-repo host compatibility layer: stub headers standing in for ESP-IDF, FreeRTOS, and heap-allocation APIs the vendor code assumes are present, a host-side flatbuffer model loader, and a <format> shim because the older host compiler doesn't ship C++20's <format> header.

Building is not the same as being correct. The first binary compiled cleanly and produced an answer for every input — but the same answer: identical, saturated embeddings regardless of what went in, so a black frame “detected a face” at the same score as a real photo. That output was deterministic and superficially resembled int8 saturation, and was initially misread that way. It wasn't. The lesson generalises: a SiL that runs and produces plausible-looking numbers has not thereby been shown faithful; it has to be checked against an independent reference, layer by layer, not just run.

That differential testing — tracing every node against an independent int8 reference, each tensor given its own private buffer — found three distinct defects, all in the vendor's generic fallback path: Conv filters shipped pre-packed for the chip's own SIMD layout that the host loader didn't unpack, a PReLU kernel that silently skipped output requantisation, and a memory planner that placed every tensor at the same offset when PSRAM wasn't configured (already fixed on esp-dl master as of commit fff487a2, June 2026, after the revision we pinned). Each was fixed as a small, documented override of the specific upstream file rather than a patch to the vendor submodule, so the fix stays visible and easy to re-check when the vendor code is updated.

The two still-present defects were reported upstream (#319, #320); the #319 fix is submitted as PR #321, with the analysis disclosed as done with Claude under Liz's direction. The project has since moved to esp-dl v3.3.9, where Espressif had already fixed the memory-planner defect — but bringing the host build up to it exposed one more host-only trap: esp-dl ≥3.3 gates every pixel conversion behind Kconfig symbols that are undefined off-device, so every frame came back “no face” until they were defined.

After all that, the SiL is bit-exact against the independent reference on every node — but that proves agreement with the reference, not with the chip. Whether its rounding matches the ESP32-S3's own arithmetic is still unproven, which is exactly why the HiL exists: the only apparatus that can close that question. The assurance takeaway is short: a SiL built from vendor code inherits the vendor's untested paths, and the real effort is in proving it faithful, not in getting it to run.

Four judges, and what each comparison isolates

The apparatus is not one system under test but four, scored on identical stimuli through identical crops, so that only the thing being compared varies. Rendering is the expensive half, so every probe image is rendered once and shown to all four:

JudgeWhat it isWhy it is in the set
HiLthe quantised model on the real ESP32-S3the deployed artefact — ground truth
SiLthe same quantised model, executed on a hostfast, fully observable, needs proving faithful
MobileFaceNet (float)the same architecture family at full precisionisolates what quantisation costs
Desktop-class (float)an unconstrained model (e.g. ArcFace R100)isolates what the power budget costs

Three comparisons fall out of that set, and each answers a different question:

SiL vs HiL — a methodology question. Do we have to run every probe on real hardware, or is a host execution of the exact same model faithful enough to stand in? If the two agree, surface mapping can be done at software speed and the device is needed only for spot checks; if they diverge, every published number has to come off the device and the throughput of the whole method changes. This is a question about how you are allowed to measure, and it has to be settled before either of the others means anything.

SiL or HiL vs float MobileFaceNet — a quantisation question. Same architecture family, full precision versus INT8. This is where the “does squeezing the model into a chip change what it accepts” question lives, and it is the comparison most likely to surface behaviour that exists only in the deployed artefact and not in anything the vendor benchmarked.

SiL or HiL vs desktop-class vs MobileFaceNet — a parameterisation question. Holding precision aside, how much of the edge model’s behaviour is down to it being small? A 1.2M-parameter MobileFaceNet and a ~65M-parameter ArcFace R100 are different answers to the same problem; comparing all three separates “small model” from “quantised model” from “this particular model”.

Making the judges comparable

Their scores are not on a common scale, so a shared numeric threshold would be meaningless. Two operating points are used instead, and results are always labelled with which one:

  • The vendor’s own default (tau = 0.5 for esp-dl) — what the deployed system actually does, the only operating point that describes the product.
  • A matched false-accept rate, with each judge’s threshold set from an impostor cohort of synthetic faces (SFHQ-T2I, MIT-licensed, so no real third-party identities are involved) — the only fair way to compare judges to each other.

Matching on genuine acceptance alone is not sufficient, and was tried first: a model that accepts everything scores perfectly on genuine pairs and appears maximally tolerant. Impostors are what make the operating point real — and in this project the impostor check immediately earned its place by exposing a landmark-ordering bug that had been silently corrupting every float judge’s input crop.

What makes hardware-in-the-loop hard

The four-judge design argues for scoring on real hardware. It says nothing about what that costs to arrange. Having a HiL rig at all is an engineering commitment that most people evaluating a face-recognition system never make — which is exactly why a vendor's own numbers usually go unchallenged: hardly anyone is set up to check them. What follows is what that commitment turned out to involve here, roughly in the order it was encountered.

The device looks dead when it is merely busy. Loading the models from flash into PSRAM takes about 30 seconds after any reset, and several early “the firmware is broken” conclusions were tests that gave up after 8–12 seconds. Anything that resets the board — including the DTR/RTS toggle the flashing tool uses to trigger the ROM loader — buys another 30 seconds of silence. Keeping the runner resident pays that cost once rather than on every exchange.

Transport is the throughput ceiling, and which transport is in use is not obvious from the outside. The board exposes two USB ports, and they behave very differently:

PortEnumerates asPractical rateNotes
UART bridge1a86:55d3 (CH343)11.5 kB/s at 115200 baudbaud is a real limit
Native USB (OTG)303a:1001 USB JTAG/serial~500 kB/sbaud setting is ignored

Over the bridge, a single 57 kB frame costs about 5 seconds. A quick way to tell the two apart without opening anything up: set a mismatched baud rate and send a command. Native USB ignores the setting and still replies; a real UART goes silent.

Flow control is not optional. The device's receive buffer is far smaller than an image, so an unpaced sender overruns it — and the lost bytes are then parsed as commands. The symptom looks like a protocol bug, an ERR UNKNOWN_COMMAND full of image data, when the actual cause is a buffer.

The peripheral can only have one owner. If the console is configured on USB-Serial-JTAG, installing the driver for the protocol asserts, because the console already owns the peripheral. The arrangement that works is console on UART0, so logs stay visible on the bridge port, with the driver owning the native USB port for the protocol itself. Getting this the wrong way round produces a device that is completely silent — indistinguishable from a hang.

Anything sharing the stream will corrupt it. Models load lazily, so a log line can appear in the middle of an exchange and be read as a reply.

The device node is not stable. Every reset re-enumerates the USB device, and under a rootless container the node can reappear with no permissions at all: the host's udev rules cover the bridge's vendor ID but not Espressif's, and neither chmod nor mknod is permitted inside the container, so this has to be fixed on the host.

The board serves one client at a time, and that client can be left mid-sentence. If it dies during a payload, the device keeps counting bytes and swallows whatever arrives next. The fix is for the client to resynchronise on connect rather than reset the board — a reset would cost the 30-second reload.

The consequence for the method: even fully optimised, the device is the slowest judge in the set — roughly 0.15 s of transfer plus 0.4 s of inference, against about 0.1 s on the host. HiL is best understood as the instrument that validates the cheap judge, not the one that carries the volume, which is why the SiL-vs-HiL comparison has to be settled before any large corpus is run.

Why both, not one

SiL earns its keep on breadth: many directions, many shells, tensor-level diagnosis, regression tests that run in seconds. HiL earns its keep on truth: it settles parity, it is where INT8 cliffs and aliasing effects that only exist in real silicon actually show up, and once parity is demonstrated it becomes the system of record for surface mapping. Neither covers every customer position on its own, which is the actual reason this project carries both rigs rather than standardising on one.

Future work

Two extensions are anticipated but not started.

An image-to-CSI-2/MIPI input adapter. For the black-box, product-only scenario, inputs currently have to be presented by pointing the product's camera at a screen. An adapter that replaces the camera sensor and injects image data directly onto the device's CSI-2/MIPI input would let the same controlled image set drive the black-box scenario that already drives the SiL and the application-level HiL.

Presentation Attack Detection (PAD). PAD — detecting spoofing attempts such as photos or masks presented to a sensor — is a distinct problem from the one this project addresses. This project maps the acceptance surface in embedding space: whether a system accepts or rejects a legitimate embedding perturbed by a known amount. PAD is about whether a presented input is a genuine live subject at all, upstream of embedding space entirely. The two are complementary and worth treating separately rather than folding one into the other.
